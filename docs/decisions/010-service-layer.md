# ADR 010: HTTP API with SQL persistence, MCP/LangChain adapters, and an evaluation tool
**Decision:** add, as optional extras around an untouched core, a FastAPI service (`api.py`) that runs briefs as background jobs and stores them in SQL (`db.py`, SQLAlchemy + Alembic; SQLite by default, Postgres by URL); a LangChain adapter over the MCP tools; an MCP client; retry with backoff at the LLM boundary; and `veritas-eval`.
**Why these choices:**
- *Jobs, not blocking requests.* A live run takes about two minutes, so `POST /briefs` returns `202` and a `run_id`. Jobs run in the app's background thread pool; there is no queue, so a restart loses a job that was running (its row stays `running`). A real deployment would put a worker queue here.
- *SQL for results.* Runs, evidence, issues and conflicts are relational and queried in aggregate (pass rate, repair histogram, top error codes), which is what `GET /stats` does. Re-validation reads the registry from SQL and reloads the documents instead of keeping state in memory.
- *One implementation per tool.* The LangChain tools call the FastMCP server object, so path confinement, error mapping and run storage are not reimplemented. The HTTP API shares `paths.py` with the MCP server.
- *Retries only for transient errors.* `RetryingLLM` retries `TransientLLMError` (CLI timeout or empty output) with exponential backoff; the Anthropic SDK already retries HTTP failures, so wrapping it again would multiply attempts.
- *Evaluation separates the model from the harness.* `veritas-eval` labels simulated stand-ins as simulated and tests them: a judge that approves everything must show zero detection.
**Costs and limits:** more surface to maintain (about ten modules, all behind extras); no authentication on the API; a single-process job runner; Alembic runs on startup, which is fine for one instance and racy for several; Docker/compose and Postgres are written but were not run where this was developed. `langchain-anthropic` is not a dependency because its current release needs a newer `anthropic` SDK than the pinned one.
**Revisit when:** the API needs auth, multiple workers (then a queue and migrations as a deploy step), or live evaluation numbers should gate changes in CI.
